01Current scope

Implemented

A native Android main screen

  • Jetpack Compose and Material 3.
  • System light and dark themes, with dynamic colour on Android 12 and later.
  • Current speed in km/h, GPS altitude, accuracy, and maximum speed.
  • Portrait and landscape layouts, large text, and screen-reader labels.
  • No home-screen scroll area. The speed display uses the space left by the readings and GPS controls.
  • Precise-location permission, pause and resume, and recovery messages.

GPS with a limited request lifetime

  • Use the Android GPS provider. Request updates once per second.
  • Release the request when the main screen becomes inactive.
  • Reject poor readings. Clear readings that are at least 10 seconds old.
  • Keep measurements in SI units. Use the current locale for display.
  • No background collection, wake lock, location upload, or trip storage.
Performance is a requirement, not a measured result yet. The device tests confirm that GPS requests stop during pause and in the background. Battery use, startup time, and frame timing still need physical-device measurements.

The local repository contains source, build files, rules, and this report. IDE state, build output, local SDK paths, and prototype exports are excluded. No remote is configured. Nothing has been pushed to GitHub.

03Verification

7 core tests + 1 layout test passed
P2 permission recovery · Fixed and verified. A review agent reproduced this defect on the API 36 emulator on 20 October 2026. After two denials, Android marked both location permissions as USER_FIXED. The app still showed “Allow precise location”. A third tap opened no dialog. The old callback could leave the settings action out of date. The fix updates observable permission state after each result and when the app resumes. A second code review found no new permission defect. The new automated test checks two denials, activity recreation, and the Android App info page. It grants permission through Android's test API, checks that no GPS request exists while Settings is open, then returns and checks speed, altitude, and the pause action. A separate direct API 36 check also passed: two denials, rotation, a grant through the Settings controls, and a restored GPS request. The automated test does not operate those Settings permission controls.

Last core device run: 20 October 2026, 13:56 PDT. Seven tests passed on the dedicated API 36 emulator. Test commands took 153.4 seconds in total. Each test ran in a separate AndroidJUnitRunner invocation, with app data cleared before each test. This run did not use Orchestrator. Tests use the production location source and Android test locations. The tested APK contains earlier layout edits. It predates the final short-window layout correction. The local evidence records APK hashes and the tested source hashes.

Final layout run: 20 October 2026. The separate layout test passed on the final debug APK. It checked 100%, 110%, and 200% text in portrait and landscape, with permission, live, paused, and location-off states. It also checked dark mode. No scroll area, clipped text, or controls outside the home content were found. The emulator used 1080 × 2340 pixels at 420 dpi, about 411 × 891 dp. This matches the connected Pixel 7 Pro's logical size at 1440 × 3120 pixels and 560 dpi. The first final run passed in 57.9 seconds. 05Future work

Proposed order · No dates assigned

The current main-screen milestone is complete. The items below remain open. They are a plan for later work, not implemented features.

Research complete · 20 October 2026

Location power and background recording

A research agent reviewed the app and official Android sources. Keep the current GPS source as a baseline. Compare it with fused location on physical devices.

  • Use a location foreground service for a trip started in the visible app. Give recording a lifecycle separate from the screen.
  • Use one shared location request. Preserve every delivered route point before producing display updates. The current stream can discard intermediate readings and cannot serve as the route recorder.
  • Test 1-second fixes with up to 10 seconds of batched delivery when the screen is off. Compare power use and route quality before selecting longer intervals.
  • Keep the live display's freshness rule separate from route history. A valid batched point can be more than 10 seconds old when delivered.

Proposed settings only. Background recording is not implemented. Battery savings remain unmeasured. Read the research findings, source links, and measurement plan. The report also records the API 37 location-button policy decision needed before publication.

Required · Before Android publication

Validate and prepare the app

  1. Complete the separate layout acceptance check and final debug lint. Repeat release lint and verify the final release build.
  2. Test GPS outdoors on physical devices. Include stationary use, movement, weak signal, and signal recovery.
  3. Measure battery use against an idle baseline. Measure cold start and frame timing in a release build.
  4. Test TalkBack, denied and approximate permission, permission revocation, and screen lock. Extend coverage to the minimum supported API and current devices.
  5. Select the final application ID and launcher artwork. Configure release signing outside Git.
  6. Complete the privacy and store requirements for the final feature set. Verify the signed release.

The current application ID is com.example.cvkegps. The release build is unsigned.

Required · For route tracking

Record and review a trip

  1. Choose a map provider and define behaviour when the device has no network connection.
  2. Add a route model and local storage. Preserve all delivered batch points, timestamps, accuracy, and recording gaps. Keep the live display's freshness rule separate from route history.
  3. Add a location foreground service started by the user, with notification controls. Use one location request and a recording lifecycle separate from the screen.
  4. Compare the current provider, fused location, batching, and update intervals on physical devices. Select settings from measured power use and route quality.
  5. Add start, pause, resume, finish, and save. Define recovery after process loss.
  6. Add trip history and route details. Verify the full recording flow with device tests.

The present GPS source stops with the screen. A recording session must have a different request lifetime.

Planned · iOS app

Keep the product consistent across platforms

  • Agree common measurement units, freshness rules, and trip data fields.
  • Create the native iOS app with its own location and permission handling.
  • Use the iOS design language for its interface.
  • Validate equivalent user flows on iOS devices. Review code sharing only when both apps need it.

No iOS project exists in this repository yet.

Optional · Select after the core works

Additional capabilities

  • Metric and imperial unit selection.
  • GPX export and explicit sharing of saved trips.
  • Offline map downloads, if the selected map provider supports them.
  • Automatic pause and activity detection, after field validation.
  • Volume-button controls and a larger speed display mode.

Each addition needs a clear user benefit and a review of battery use, privacy, and test scope.
