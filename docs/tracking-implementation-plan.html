1. First delivery

Agreed scope: include online maps in the first release. Implement local recording before map integration. A map failure must not stop a recording. The recorder must work without a network connection.

  • Select Car, Transit, Plane, Bike, or Ski before Start. Use one mode per trip initially.
  • Start from the visible app. Continue after Home or screen lock through a location foreground service.
  • Provide manual Pause, Resume, and Stop. Save points during the trip. Stop saves the final state.
  • Show recording state, elapsed recording time, current speed, recorded distance estimate, and signal quality.
  • List saved trips. Open a trip to see its mode, times, distance estimate, readings, and interruption periods. Allow the user to delete a trip with confirmation.
  • Recover the last saved data after process loss. Mark the trip Interrupted. Offer Resume or Finish when the app is visible.

Online route review is required before the first delivery is complete. Keep the trip summary available when the map cannot load. Do not add an inactive map control.

Defer automatic pause, activity detection, navigation, cloud sync, accounts, GPX export, and ski-run detection. Add these features only after the user selects them.

2. Activity modes

Modes select presentation first. Keep measured values and quality fields in the saved record. Do not infer better accuracy from an activity label.

Store linear measurements in SI units and angles in radians. Convert only at platform boundaries and for display. Keep missing measurements nullable. Format display values for the user's locale. Keep km/h and metres initially; knots and feet can follow the flight-unit decision.

Identify the altitude reference. Android GPS altitude is normally relative to the WGS84 ellipsoid. Store mean-sea-level altitude separately only when the platform supplies it with a known reference. Do not silently label one as the other. A personal flight record is not a navigation instrument.

3. Maps

Separate the map renderer, map data, and saved route. One renderer can show different styles. A map style does not change GPS accuracy. Do not add a separate SDK for each activity.

First map milestone

Show the measured route, start and end points, and separate segments at gaps. Let the user pan and zoom. Keep the trip summary available if map data cannot load.

Use MapLibre Native with standard OpenStreetMap tiles, as selected by the user. Check attribution, an identifying User-Agent, caching, request limits, and the tile-use policy before release.

Offline and specialist maps

If offline maps are required, define download areas, size limits, deletion, and map-data updates before SDK selection. Cached online tiles are not an offline-download promise.

Aviation and ski layers need suitable source coverage and permission to display and store the data. Do not assume public map tile servers permit bulk downloads.

Map requests can disclose the viewed area to a provider. Document that behaviour before adding network access. Keep trip points out of analytics, logs, and crash reports. Keep local storage excluded from backup. Do not upload routes or add cloud sync.

The first renderer and tile source are selected. Specialist map sources and offline downloads remain deferred. The OpenStreetMap tile policy was checked during implementation. Provider benchmarks and specialist-source licence reviews remain open.

4. Recording design

One Android location request → recording coordinator → local database.
The same coordinator supplies the latest reading to the screen.

Location ownership

Keep LocationManager.GPS_PROVIDER as the first provider. Introduce a small batch-capable source interface. Android types stay in its adapter. Preserve every delivered point before producing the latest display state.

The current AndroidGpsSource uses conflate(). Its reading model has no coordinates or UTC time. The ViewModel rejects readings at least ten seconds old. Keep this display rule separate from valid historical samples.

  • Use one coordinator with a defined coroutine scope and constructor injection. It owns the source while recording or while the live screen needs GPS.
  • During recording, the service owns the session lifetime. Screen recreation must not add a request. When no trip is active, preserve the current screen-only lifetime.
  • Trip Pause stops measurement collection, including the live speed request. Resume starts a new segment. Stop removes the recording request. A visible speedometer can then resume its own explicitly active display request.
  • Keep GNSS satellite status separate. It is needed only for the visible satellite display, not for route storage.
  • Start with high accuracy, a one-second interval, immediate delivery, and a zero-metre distance filter for all modes. These are test settings, not measured optimum settings.
  • Use a bounded queue. Check enqueue results. On overflow or a storage error, stop collection and show an error. Preserve the committed route. Record a gap when storage permits. Never report an uninterrupted saved route after loss.

Local records and calculations

Use Room for durable sessions, transactions, and queries. The implementation uses Room 2.8.5 and KSP 2.3.12 from the version catalog. Do not add a dependency before it is used.

  • Trip: ID, mode, state, start and end UTC time, and calculation-policy version.
  • Segment: trip ID, recording-run ID, order, start and end time, and interruption reason. Distinguish manual pause, signal loss, access loss, and process interruption.
  • Point: coordinates, UTC and elapsed-realtime timestamps, arrival time, provider, speed, altitude reference, track, available uncertainty, and test-location flag.
  • Use elapsed realtime for duration and order within one recording run. Create a new run after a restart. Never compare monotonic timestamps across a reboot. UTC clock changes must not produce negative duration.
  • Deduplicate by run and measurement identity. Handle late and reordered batch points without dropping valid history. Use command boundaries to keep points measured during a pause out of the active segment.
  • Write points and session state together off the main thread. Proposed initial limit: commit at least once per second while points arrive. Measure actual commit delay; the limit cannot guarantee survival of abrupt device power loss.
  • Keep raw valid measurements separate from summary eligibility. Invalid coordinates or times must not enter a route. Poor accuracy can remain in history with its quality flag.
  • Calculate geodesic distance only within accepted continuous segments. Do not count a straight line across a gap. Test stationary drift, poor fixes, the date line, and polar routes. Report a recorded-distance estimate with missing-time information.
  • Use reported speed for current and maximum speed only when its quality is acceptable. The current 50 m position and 3 m/s speed thresholds are provisional. Do not impose a car speed limit on plane data.
  • Exclude manual pauses from recording duration. Show signal-gap duration separately. Defer moving time and moving-average speed until stop detection has an agreed definition.

Service, permission, and recovery

Use these states: Idle → Recording → Paused → Recording → Finished. Recording can also enter Interrupted or Error. Process all commands in one ordered path. Repeated Start and Stop commands must be safe.

  • Explain precise location and notification use before requesting access. Start only from an explicit action in the visible app.
  • Declare FOREGROUND_SERVICE, FOREGROUND_SERVICE_LOCATION, POST_NOTIFICATIONS, and service type location where required. Do not request ACCESS_BACKGROUND_LOCATION for this user-started flow.
  • Show a visible recording notification with Pause or Resume and Stop. Update it at a limited rate. If notification access is denied, disable Start and Resume. Explain the missing access and offer Settings.
  • Verify current foreground-service rules for each supported Android version. Start from the visible activity; if a paused service cannot resume from a notification action, open the activity to resume.
  • On GPS loss or disabled location, mark the gap and show the cause. On permission loss, release the request and require access recovery.
  • On reopen, detect unfinished saved sessions and mark them Interrupted. Do not silently restart after force-stop, Task Manager Stop, or reboot. Resume creates a new segment and preserves the earlier data.
  • On Stop, commit queued points, remove callbacks, then finish the service. The current request does not use batching; no provider flush is requested. Do not rely on onDestroy() to save a trip.
  • Do not add wake locks, an always-on screen, scheduled GPS polling, or battery-exemption requests.

6. Small test set

Use the production Android location path with Android test locations. Extend the existing device-test setup. Always restore permission, notification, location, display, and power settings. Remove test providers in cleanup.

  1. Record and save: choose a mode, Start, deliver points, rotate, press Home, lock, unlock, Pause, Resume, then Stop. Check saved points, separate segments, notification actions, and one active location request.
  2. Access and signal recovery: deny precise or notification access, recover through Settings, disable and restore GPS, then remove location permission. Verify unavailable readings, visible gaps, and cleanup.
  3. Interrupted trip: save points, force-stop from an external device driver, reopen, then Resume or Finish. Check committed data and no silent restart. Include one injected storage-write failure.
  4. Saved-trip UI: open and delete a trip. Check large text, light and dark themes, rotation, and screen-reader labels. Check a map-loading failure and the selected offline behaviour.

Add only focused unit tests for distance and time rules, duplicate or reordered points, pause boundaries, and queue overflow. These cases are hard to reproduce reliably through device GPS. Use a small parameterized set, not a test for every getter or state assignment.

For functional changes, run assembleDebug, Android lint, and the relevant device tests. Test API 29 and the current target API 37; existing API 36 evidence does not prove either boundary. Before release, run the release build and release lint.

Physical tests must cover car, transit signal gaps, plane reception, bike curves and tree cover, and ski movement. Include long screen-off use, Doze, Battery Saver, another phone manufacturer, and a stationary control. Simulated GPS proves flow behaviour only. It does not prove battery use or accuracy.

7. Open decisions and completion limits

  • Agreed first delivery: recorder, saved trips, trip review, and online maps. Offline downloads are deferred.
  • Agreed flight use: personal record. Use km/h and metres initially. Knots and feet remain optional future work.
  • Agreed trip modes: one manually selected mode per trip. No automatic detection.
  • Before later map work: specialist coverage, offline regions, and acceptable provider cost. The first map needs no API key or Google Play services.
  • Before field acceptance: acceptable route error, speed uncertainty, battery use per hour, and maximum unsaved time. Set these limits with device measurements; do not invent accuracy claims.

Use local-only trip storage, no automatic resume, and the current GPS provider. Selected map provider: MapLibre with standard OpenStreetMap tiles. The integration includes attribution and an identifying User-Agent. Recheck the tile policy before publication.
